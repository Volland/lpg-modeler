Migrating a deployed model

emit produces the schema a database should have. Once one is deployed, you need the steps from the schema it has. A committed lockfile records what was deployed, and lpg migrate writes the scripts that carry it to the current model.

1. Write the element ids

A migration tells a rename from a removal by each element’s id. A model written by hand has ids derived from names, and those follow a rename, so a renamed property would be migrated as a dropped column and a new one. lock, diff and migrate refuse such a model. Write the ids once and commit them: 

$ lpg ids model/domain.lpg.yaml
assigned 14 id(s) in /work/model/domain.lpg.yaml

2. Record the baseline

The lockfile must describe what is deployed, not what is on your branch. Check out the commit the database was built from, lock there, and commit the lockfile: 

$ git checkout <deployed-commit> -- model/domain.lpg.yaml
$ lpg lock model/domain.lpg.yaml
/work/model/domain.lpg.lock.json (revision 1)
$ git checkout HEAD -- model/domain.lpg.yaml

If the deployed schema already matches your current model, lock the current model instead.

3. See what changed

Every change is matched by id and classed additive (nothing existing becomes invalid), breaking (existing data or queries may stop fitting) or destructive (stored data is removed): 

$ lpg diff model/domain.lpg.yaml
additive    property Person.phone: added as string
breaking    property Person.mail: renamed from 'email'
1 breaking, 1 additive since revision 1

In CI, --fail-on breaking turns that into a gate on the pull request.

4. Generate the scripts

$ lpg migrate model/domain.lpg.yaml
/work/model/migrations/domain.0002.ladybug.cypher
/work/model/migrations/domain.0002.neo4j.cypher
/work/model/migrations/domain.0002.falkordb.sh
/work/model/migrations/domain.0002.memgraph.cypher
/work/model/domain.lpg.lock.json (revision 2: 1 breaking, 1 additive)

Review the scripts and commit them with the lockfile. Each one lists the changes it realizes at the top. migrate never connects to a database, so running them is up to you — or, for Memgraph, to lpg apply: 

# LadybugDB: statements run in order with no enclosing transaction; back up first.
# Neo4j: data steps use CALL { ... } IN TRANSACTIONS, so run in auto-commit mode.
cypher-shell -f model/migrations/domain.0002.neo4j.cypher
# FalkorDB: not idempotent; run once against a graph at the previous revision.
GRAPH_KEY=domain sh model/migrations/domain.0002.falkordb.sh
# Memgraph: one command, stopping at the first refused statement.
lpg apply model/migrations/domain.0002.memgraph.cypher --target memgraph --uri bolt://localhost:7687

Destructive changes

A migration that would discard stored data is refused, and a refusal writes nothing: no script, and the lockfile keeps its revision. That covers a removed type or property, and also a change the model calls merely breaking that a target can only apply by discarding data. LadybugDB cannot change a primary key, a column type or a multiplicity in place, so it recreates the table or column instead. 

$ lpg migrate model/domain.lpg.yaml
error destructive-change: property Person.nickname removed, which discards data.
Nothing was written. Pass --allow-destructive to generate it anyway.

With --allow-destructive, every such statement is preceded by a DESTRUCTIVE: comment naming what it drops.

What is migrated

Only the database targets hold a schema to carry forward: ladybug, neo4j, falkordb and memgraph. SHACL, OWL, GQL, PG-Schema and LinkML are regenerated with emit. The lockfile is per model, so migrate every deployed target in the same run; naming only some of them is allowed, with a warning. A change no target stores, such as a value pattern, still advances the revision, and each script says it has no schema effect.
